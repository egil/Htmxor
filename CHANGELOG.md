# Unreleased

## Breaking changes

- `HtmxRequest.TryGetExtensionHeader(string, out string)` and `HtmxResponse.SetExtensionHeader(string, string)` provide the bounded beta seam for application-owned extension fields. They accept only unprotected `HX-*` field names, reject core and `HXOR-*` ownership, preserve one valid value exactly, enforce an ASCII header-safe 4096 UTF-8-byte limit, and never create route, method, action, authorization, antiforgery, cache, or general-HTTP authority. Use `HttpContext` directly for non-`HX-*` or intentionally multi-valued application fields.
- Htmxor now parses the seven core htmx 4 request headers once through field-specific policies. `HX-Request` must be exactly one normalized lowercase `true` before dependent context is exposed; `HX-Request-Type` recognizes only `full` or `partial`, with only `partial` selecting direct routing; boolean boost and history headers recognize only one normalized lowercase `true`; `HX-Current-URL` is one untrusted absolute HTTP(S) `Uri`; and `Source` and `Target` preserve one exact nonblank open string after HTTP optional-whitespace trimming. Missing, malformed, repeated, contradictory, control-containing, or ill-formed values fail closed as documented. `HtmxRequest.CurrentURL`, `HtmxRequestHeaderNames.CurrentURL`, and `HtmxRouteAttribute.CurrentURL` are now `CurrentUrl` with no compatibility aliases. Current-URL route filters resolve relative declarations against the parsed URL, compare scheme/host/port using URI rules, and keep path/query comparison ordinal and case-sensitive; these client hints never authorize methods, actions, or access.
- `HtmxResponse.Reswap(string)`, `Retarget(string)`, and `Reselect(string)` now treat their argument as one complete open htmx or extension value. They reject null, empty, whitespace-only, surrounding whitespace, and values containing control characters before the strict htmx-request guard, preserve valid values exactly, overwrite only their own response header, coexist with one another, return the same response instance, and leave status and body behavior unchanged. The incomplete public `SwapStyle` enum, `Reswap(SwapStyle, string?)` overload, and converter have been removed; pass the complete value to `Reswap(string)` instead.
- `HtmxResponse` navigation operations now expose `Location`, `PushUrl`, `Redirect`, and `ReplaceUrl` with `string` and `Uri` destinations, plus the two explicit history-prevention methods and `Refresh`. They reject invalid URI references before the htmx-request guard, preserve exact string or `Uri.OriginalString` text, enforce HTTP(S) origin rules, emit exactly one last-call-wins navigation header, and apply the documented response-body effect without changing the response status. Explicit `EmptyBody()` remains independently suppressing within that component render. `Location(LocationTarget)`, `LocationTarget`, and `AjaxContext` have been removed; use `Location(string)` or `Location(Uri)` instead.
- A forced component navigation that also requests replacement history now emits one `HX-Redirect` for the required full page load. It no longer emits a conflicting `HX-Replace-Url`; replacement-history parity is not claimed for that combination.
- Navigation body suppression is render-local. Before an unstarted suppressed response is written, Htmxor clears a positive declared `Content-Length`; the suppressed `WriteAsync` overloads returning `Task` and `ValueTask` preserve pre-canceled tokens; and a later error-handler component render on the same `HttpContext` starts with fresh body-control state. Direct stock 302 adaptation validates the redirect before changing status or removing `Location`, so an invalid stock redirect remains unchanged.
- Htmxor now recognizes an htmx request only when `HX-Request` contains exactly one value that equals lowercase `true` after trimming surrounding HTTP optional whitespace (space or tab). Missing, blank, `false`, malformed, comma-joined, or repeated markers keep the stock or not-found path, ignore dependent `HX-*` context, and cannot use the guarded Htmxor response operations. Raw `HtmxResponse.Reswap(string)` now follows the same request guard as the other covered operations.
- Service and endpoint registration now use the product-named `AddHtmxor()` and `AddHtmxorEndpoints()` pair. Remove calls to the former beta names `AddHtmx()` and `AddHtmxorComponentEndpoints()`; no compatibility aliases are provided.
- `HtmxFragment` is now the only server-side fragment-selection component. It remains wrapperless by default and can optionally emit `Element`, `Id`, and unmatched HTML attributes; remove `HtmxFragmentElement` call sites and put those parameters directly on `HtmxFragment`. Add `hx-swap="outerHTML"` explicitly when migrating a call site that relied on `HtmxFragmentElement`'s former implicit swap. htmx 4 `<hx-partial>` delivery envelopes can be authored as `HtmxFragment Element="hx-partial"` with ordinary `hx-target` and `hx-swap` attributes, or as raw application markup inside a wrapperless fragment.
- Htmxor request representation now follows htmx 4's `HX-Request-Type`: only `partial` uses direct component output, while `full`, missing, blank, unknown, or contradictory values retain the stock page path. Use nullable `HtmxRequest.RequestType` (`Full` or `Partial`) and replace request `Trigger`/`TriggerName` reads with the complete raw `Source` identity. `Target` now contains `tag#id` or a tag-only identity rather than an id alone. The request `Trigger`, `TriggerName`, and `Prompt` properties and header constants, plus `HtmxRoute.Trigger` and `TriggerName`, have been removed; optional prompt-extension headers remain available through `HttpContext.Request.Headers`.
- Htmxor now emits response events only through one compact htmx 4 `HX-Trigger` JSON object. Event names are validated as well-formed UTF-16 and safely JSON-encoded as exact, case-sensitive property names. Distinct calls append in wire-member order; a later call for the same name replaces its detail without moving its first position. A missing detail, or any detail that serializes to JSON null, uses `{}` because htmx 4.0.0 does not dispatch a JSON-null detail. Detail data uses the application's ASP.NET Core JSON options unless the call supplies `JsonSerializerOptions`; Htmxor owns the final compact, header-safe encoding, so `Encoder` and `WriteIndented` do not control the header representation. Invalid input, detail-serialization failure, or an invalid htmx request marker changes no response state. The first successful Htmxor call replaces any manually supplied `HX-Trigger`, while every successful call returns the same response and leaves status and body behavior unchanged. Remove the `TriggerTiming` argument from `HtmxResponse.Trigger(...)` calls; htmx 4 dispatches these response events after the swap completes. The `TriggerTiming` type and the `TriggerAfterSwap` and `TriggerAfterSettle` response-header constants remain removed.
- The public client-side `Constants` and trigger facade/builders, plus `SwapStyleBuilder`, `SwapStyleBuilderExtension`, `ScrollDirection`, and the builder-based `HtmxResponse.Reswap(...)` overload, have been removed. Write native htmx attribute values directly as Razor strings. `HtmxResponse.Trigger(...)` remains available for the server response contract.
- `HtmxResponse.StopPolling()` and `HtmxStatusCodes` have been removed. htmx 4 polling ends by returning replacement markup without the polling attributes; use the [native polling pattern](docs/htmxor-v1-feature-guide.md#polling). `HtmxResponse.StatusCode(HttpStatusCode)` remains general HTTP status control, including a deliberate numeric 286 when an application needs it; Htmxor assigns no polling meaning to that status.
